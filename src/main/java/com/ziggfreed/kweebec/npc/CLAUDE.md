# npc/ - where the Grove Warden stands

Router for `npc/`. **The Grove Warden is stood up by `ziggfreed-common`'s NPC placement engine** ([`com.ziggfreed.common.npc.placement`](../../../../../../../ziggfreed-common/zc-dialogue/src/main/java/com/ziggfreed/common/npc/placement/CLAUDE.md)), not by any spawner of kweebec's own: this mod ships ONE placement asset and the engine owns the ledger, the per-boot sweep, the orphan despawn and the gate chain. That is the lift paradigm applied - a generic Hytale primitive belongs in the library, and the consumer keeps only the content.

- **The asset is [`Server/ZiggfreedCommon/NpcPlacements/Kweebec_Grove_Warden.json`](../../../../../resources/Server/ZiggfreedCommon/NpcPlacements/Kweebec_Grove_Warden.json)**, folded by the library like any other mod's: `Identity.Role` names `KweebecNightmare_Guide`, `Where` matches the `default` world, `Anchor.WorldSpawn` offsets 5 blocks along X at yaw 90, and `Lifecycle` opts into `KeepAlive`/`Respawn`/`Fortify` because an entry NPC that can be killed or lost takes every player's way into a round with it. Round instances and the creative hub fire `PlayerReadyEvent` too, and they are kept Warden-free by not matching `Where`, never by a special-case check.
- **`Requires` gates the Warden on MMO Skill Tree being ABSENT** - `{"Factor": "hytale:mod_installed", "Param": "Ziggfreed:MMOSkillTree", "Max": 0}`. A server running both mods already has a guide at spawn, so there the Warden is placed deliberately with the native NPC spawn tooling instead of appearing on its own. `Max: 0` rather than a bounds-less condition is deliberate: an absent mod reads a definite `0`, and a bounds-less condition passes any non-null finite value, so it would pass whether the mod were installed or not (`ModFactors` javadoc says so in full). **The owner override file cannot un-gate this** - `mods/ziggfreedcommon/npc-placements.json` carries only `enabled`, and `PlacementGates` runs the owner override BEFORE the authored `Requires` with any deny winning. A server that wants the Warden at spawn alongside the MMO ships its own file with the same id and no `Requires` block; the asset's `$Comment` tells the owner exactly that.
- **Press-F wiring is in the role asset, not here, and NOT on the placement.** `Server/NPC/Roles/KweebecNightmare/KweebecNightmare_Guide.json` (a `Type: Generic` Passive role copied from the MMO's `MMO_QuestGiver`) carries the `InteractionInstruction` that fires `{ "Type": "ZigOpenDialogue", "Dialogue": "nightmares_intro", "ContextNpc": "guide" }`. The action and its `ZigOpenDialogue` registration are common's; the plugin calls `NpcActions.register()` in `setup()` BEFORE the role asset loads, or `{ "Type": "ZigOpenDialogue" }` fails to parse. Nothing else is registered to make the screen work: the conversation page is common's and composes from process-wide state, so [`../dialogue/KweebecDialogue`](../dialogue/KweebecDialogue.java) only contributes this mod's action/condition types and declares its key namespace.
  - **Why the role keeps `ZigOpenDialogue` instead of the placement's `ZigPlacementInteract`.** `ActionPlacementInteract` reads the NPC's own `PlacedNpcComponent` to find the placement behind it, and an NPC an admin spawns through native role tooling carries no stamp, so press-F would do nothing at all. Since the whole point of the gate above is that a both-mods server places the Warden by hand, the role has to be the one that knows what it opens. The placement therefore authors NO `Interact` block, and the Warden talks whether the engine stood it up or a person did.
- **[`LegacyGuideFiles`](LegacyGuideFiles.java)** retires the two owner files kweebec's own spawner kept, `guide.json` and `guide-placements.json`, renaming each in place to `.legacy` and logging ONE boot notice naming the replacement. It never reads either file and never deletes either file; a name already taken gets a numbered suffix so a second boot cannot overwrite the first copy. **Nothing is carried across** - a world list, an offset and a yaw do not map onto a placement asset without guessing, and a guessed placement puts the Warden somewhere the owner never asked for. Called from [`KweebecNightmarePlugin.setup`](../KweebecNightmarePlugin.java); pure `java.nio.file` I/O, safe before the asset pipeline exists, and it never throws.
- **A Warden already saved into an existing world keeps standing.** The engine's orphan sweep is over `PlacedNpcComponent`, and an NPC an older build placed carries none, so the gate cannot reach it. On an upgrading server that runs both mods the old Warden stays where it is until an admin removes it; a fresh world gets the gated behaviour immediately.
- **The Clash Host is a separate arrangement** and is untouched by any of this: it is not auto-placed at all, and `/kweebec clashhost` drops one deliberately via common's `NpcAutoSpawn`.
